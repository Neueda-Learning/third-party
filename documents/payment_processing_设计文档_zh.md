# 支付处理系统设计文档

## 1. 文档目的

本文档基于《支付处理系统训练项目》需求，给出一份可落地的系统设计方案，覆盖前后端架构、数据模型、API 设计、状态机、错误处理、测试策略与四人团队分工。

本文档的目标是帮助团队快速形成统一方案，先实现最小可用版本，再逐步扩展。

## 2. 设计目标

1. 实现一个可演示、可测试、可扩展的支付处理系统。
2. 支持支付从创建、校验、发送、完成到失败的完整生命周期。
3. 保留完整审计轨迹，便于追踪每次状态变化。
4. 提供清晰的 REST API，便于前端接入和后续扩展。
5. 采用简单、稳定、适合训练项目的技术方案，避免过度设计。

## 3. 设计原则

1. 先做最小闭环，再做增强功能。
2. 业务规则放在后端，前端只负责展示和交互。
3. 状态迁移必须受控，不能由前端任意修改。
4. 每次状态变化都要写入审计历史。
5. 接口和错误码保持稳定，便于前端处理。
6. 幂等性、并发控制、异常处理要尽早考虑。

## 4. 总体架构

系统采用前后端分离架构：

```text
┌──────────────────────────────────────────┐
│              前端 Web UI                  │
│  创建支付 / 列表 / 详情 / 历史 / 错误展示   │
└───────────────────┬──────────────────────┘
                    │ HTTP/REST
┌───────────────────▼──────────────────────┐
│               API 控制层                  │
│  接收请求 / 参数校验 / 返回响应            │
├──────────────────────────────────────────┤
│               业务服务层                  │
│  支付校验 / 状态机 / 幂等 / 处理流程       │
├──────────────────────────────────────────┤
│               数据访问层                  │
│  PaymentRepository / HistoryRepository   │
└───────────────────┬──────────────────────┘
                    │
┌───────────────────▼──────────────────────┐
│                 数据库                    │
│  Payment / PaymentHistory / Idempotency   │
└──────────────────────────────────────────┘
```

### 架构说明

1. 前端负责页面和用户交互，不直接处理业务规则。
2. 后端 API 层负责请求入口、参数合法性检查、HTTP 状态码映射。
3. 业务层负责支付生命周期、状态迁移、幂等判断、错误归一化。
4. 数据访问层负责和数据库交互，尽量不包含业务逻辑。
5. 数据库保存支付主表、历史表和幂等信息。

## 5. 技术方案建议

最终确认的技术栈如下：

1. 后端：Spring Boot + JDBC
2. 数据库：MySQL
3. 前端：HTML + CSS + JavaScript
4. API 文档：OpenAPI / Swagger
5. 版本控制：Git + 分支 + Pull Request

说明：

1. 后端使用 Spring Boot 负责 REST API、业务层和事务控制。
2. JDBC 用于直接访问 MySQL，适合把数据访问层设计得更清晰。
3. 前端使用原生 HTML、CSS、JavaScript，便于快速实现页面和交互。
4. Swagger/OpenAPI 用于接口说明和联调。

## 7. 状态机设计

### 7.1 状态定义

1. CREATED：支付已创建，等待校验。
2. VALIDATED：支付校验通过，准备发送。
3. SENT：支付已发送到目标系统。
4. COMPLETED：支付处理成功。
5. FAILED：支付任意阶段失败。

### 7.2 合法状态迁移

```text
CREATED -> VALIDATED
CREATED -> FAILED
VALIDATED -> SENT
VALIDATED -> FAILED
SENT -> COMPLETED
SENT -> FAILED
```

### 7.3 状态机规则

1. 不能从 COMPLETED 回到 CREATED。
2. 不能从 FAILED 继续前进到其他状态，除非重新创建新支付。
3. 每次状态变化都必须写入 PaymentHistory。
4. 状态变更必须校验当前状态，禁止非法迁移。
5. 所有状态更新应在事务中完成，避免主表与历史表不一致。

### 7.4 状态机实现建议

可以采用以下方式之一：

1. 简单枚举 + 服务层校验。
2. 显式状态机表。
3. 状态转换规则字典。

对于训练项目，推荐“枚举 + 服务层校验”，简单易懂且足够稳定。

## 8. API 设计

### 8.1 创建支付

`POST /payments`

用途：创建一笔支付。

请求示例：

```json
{
  "sourceAccount": "ACC001",
  "destinationAccount": "ACC002",
  "amount": 125.50,
  "currency": "USD",
  "reference": "invoice-20260727"
}
```

建议请求头：

1. Idempotency-Key: 用于防重复提交。

响应：

1. 201 Created：创建成功。
2. 409 Conflict：幂等键重复。
3. 400 Bad Request：参数校验失败。

### 8.2 查询支付详情

`GET /payments/{id}`

用途：查询单笔支付当前状态和详细信息。

响应内容建议包含：

1. 基本支付信息
2. 当前状态
3. 错误信息（如失败）
4. 创建时间、更新时间

### 8.3 查询支付列表

`GET /payments`

用途：分页查询支付，支持过滤。

建议查询参数：

1. status
2. reference
3. page
4. size
5. fromDate
6. toDate

### 8.4 查询状态历史

`GET /payments/{id}/history`

用途：查看支付所有状态变更记录。

返回应按时间升序排列，方便前端绘制时间线。

### 8.5 手动触发流程操作

如果训练期间需要把流程拆开演示，可设计以下内部接口：

1. `POST /payments/{id}/validate`
2. `POST /payments/{id}/send`
3. `POST /payments/{id}/complete`
4. `POST /payments/{id}/fail`

说明：

1. 这些接口更适合训练演示，不一定暴露给真实业务用户。
2. 实际生产中，validate/send/complete 更适合由内部流程或异步任务驱动。

## 9. 校验规则设计

### 9.1 金额校验

1. 金额必须大于 0。
2. 金额不能超过系统上限。
3. 小数位数必须符合币种规则。

### 9.2 币种校验

1. 币种必须是合法 ISO 4217 代码。
2. 系统只接受支持的币种集合。

### 9.3 账户校验

1. sourceAccount 和 destinationAccount 不能相同。
2. 账号格式必须合法。
3. 账号必须存在于系统定义的账户集合中。

### 9.4 状态校验

1. 只能进行允许的状态迁移。
2. 非法迁移返回明确错误码 INVALID_STATUS_TRANSITION。

## 10. 幂等性设计

### 10.1 设计目标

用户重复点击提交时，不应创建重复支付。

### 10.2 实现方案

1. 客户端在创建支付时传入 Idempotency-Key。
2. 后端先查询该幂等键是否已存在。
3. 如果存在且请求内容一致，直接返回已有支付。
4. 如果存在但请求内容不一致，可返回冲突错误。

### 10.3 推荐行为

1. 首次请求：创建新支付并返回 201。
2. 重复请求且内容一致：返回原支付信息。
3. 重复请求且内容冲突：返回 409 Conflict。

## 11. 错误处理设计

### 11.1 响应格式建议

统一错误响应结构，例如：

```json
{
  "errorCode": "INVALID_AMOUNT",
  "message": "金额必须大于 0",
  "traceId": "abc123"
}
```

### 11.2 错误码映射

1. VALIDATION_FAILED -> 400
2. INSUFFICIENT_FUNDS -> 400
3. INVALID_ACCOUNT -> 400
4. INVALID_CURRENCY -> 400
5. INVALID_AMOUNT -> 400
6. DUPLICATE_PAYMENT -> 409
7. INVALID_STATUS_TRANSITION -> 400
8. PAYMENT_NOT_FOUND -> 404
9. PROCESSING_ERROR -> 500
10. NETWORK_ERROR -> 503

### 11.3 设计原则

1. 错误信息要对前端友好。
2. 错误码要稳定，可用于程序判断。
3. 不要把内部堆栈直接返回给客户端。
4. 统一在全局异常处理器中转换错误格式。

## 12. 审计与日志设计

### 12.2 应用日志

1. 请求 ID / traceId
2. 支付 ID
3. 状态变化

### 12.3 日志目标

2. 方便演示。
3. 方便后续扩展到更严格的审计场景。

## 16. 并发与一致性

### 16.1 并发问题

可能出现的场景：

1. 两个请求同时更新同一支付。
2. 重复提交导致重复创建。
3. 状态迁移与历史记录写入不一致。

### 16.2 应对策略

1. 使用事务保证主表和历史表一致。
2. 使用乐观锁 version 防止并发覆盖。
3. 使用幂等键防止重复创建。
4. 对非法并发冲突返回 409。

## 18. 四人团队分工建议

虽然每个人都要同时参与前后端，但可以按“纵向切片”分工，每人负责一个业务子域的前后端联动。

### 18.1 成员 A：创建与幂等

职责：

1. 后端：POST /payments、输入校验、幂等键处理。
2. 前端：创建支付页面、表单验证、提交反馈。
3. 测试：重复提交、非法金额、非法币种。

### 18.2 成员 B：状态机与流程控制

职责：

1. 后端：validate / send / complete / fail 流程。
2. 前端：详情页操作按钮、状态变化展示。
3. 测试：合法迁移、非法迁移、失败状态。

### 18.3 成员 C：查询与历史

职责：

1. 后端：列表查询、详情查询、历史查询。
2. 前端：列表页、筛选、搜索、时间线。
3. 测试：分页、筛选、历史顺序。

### 18.4 成员 D：质量、可靠性与工程化

职责：

1. 后端：统一异常处理、traceId、并发控制。
2. 前端：错误展示、空状态、加载态、失败提示。
3. 测试与工程：CI、接口契约、回归测试、演示脚本。

## 19. 协作流程建议

### 19.1 分支策略

1. main 保持可运行。
2. 每人使用自己的 feature 分支。
3. 通过 PR 合并到主分支。
4. 合并前至少一人审查。

### 19.2 迭代节奏

1. 第 1 天：项目骨架、数据模型、创建接口、创建页面。
2. 第 2 天：状态机、详情页、历史记录。
3. 第 3 天：列表、筛选、错误处理。
4. 第 4 天：幂等、并发、测试补齐。
5. 第 5 天：联调、文档、演示准备。

### 19.3 每日同步

1. 早上简短站会。
2. 下午对齐风险与阻塞。
3. 每天至少一次合并主分支，减少冲突。

## 21. 需要确认的前提项

以下项目已确认如下：

1. 后端技术栈：Spring Boot + JDBC。
2. 数据库：MySQL。
3. 前端技术栈：HTML + CSS + JavaScript。

以下项目仍建议团队内部统一约定：

1. 是否需要把 validate/send/complete 暴露为手动接口，还是仅用于内部流程。
2. 幂等键重复时，是返回 200 还是 201，团队需统一约定。
3. 支付数据最小字段集是否需要 sourceAccount 和 destinationAccount，还是第一版先只做金额、币种、状态。
4. 是否需要在第一版就实现乐观锁，还是先在后续增强加入。

## 22. 结论

本设计建议采用“前后端分离 + 分层后端 + 状态机 + 幂等控制 + 审计历史”的方式实现支付处理系统。

该方案的优点是：

1. 结构清晰。
2. 容易实现。
3. 易于测试。
4. 易于演示。
5. 便于四人团队并行开发。

如果团队优先目标是快速交付训练项目，建议先完成：

1. 创建支付。
2. 支付详情查询。
3. 状态历史。
4. 基础状态迁移。
5. 幂等和错误处理。

在此基础上再继续扩展高级功能。
